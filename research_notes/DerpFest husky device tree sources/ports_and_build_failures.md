Method: GitHub REST API (branch lists, commit lists, commit diffs, code search), GitLab API for PixelOS GMS, raw makefile reads, two aggregator pages, and the user's local Evolution X cnb husky port (primary evidence of failures actually hit). Commit dates are committer dates from the API. "Verified" = read in the cited file/commit; "Inference" = my reasoning from those files.

## 1. Which Android 17 husky/shusky/zuma tree sources exist, and how do they differ from LineageOS lineage-24.0?

### Takeaway
Every Android 17 husky tree found is a LineageOS lineage-24.0 fork (Michael Bestas's commits underneath), with a thin ROM layer on top. **DerpFest-Devices has no Android 17 (`17`) branch for shusky/zuma/vendor_google_husky yet** (newest is `16.2`, July 2026), so a DerpFest 17 husky build has to start from LineageOS lineage-24.0 (or crDroid 17.0) and re-apply DerpFest's 16.2 fixes. Official Evolution X cnb trees exist but are mostly blunt `BUILD_BROKEN_*`/`DISABLE_ARTIFACT_PATH_REQUIREMENTS` flags plus branding. Note: LineageOS added face-unlock commits on 2026-10-16 that most forks don't have yet.

## 2. Which build errors hit when LineageOS husky trees meet a GMS-bundling ROM, and what fixes each?

### Takeaway
Six collision classes are real. Each was hit by the user's Evolution port, crDroid, RisingOS or DerpFest 16.2:
1. Soong module and install-path duplicates (DeviceIntelligenceNetworkPrebuiltAstrea; AICore).
2. Duplicate PRODUCT_COPY_FILES destinations (sysconfig XMLs, default-permissions.xml).
3. RRO module or package name collisions with ROM overlays.
4. generic_system.mk artifact-path errors for GMS /system apps.
5. Variables set in the wrong makefile type (the "read only" error).
6. Runtime-only problems: gpuflag init abort, system_other odex.

For DerpFest 17 with PixelOS gms-17, #4 is already handled by DerpFest's vendor, #3 is mostly avoided because gms-17 suffixes its overlays `_GMS`, and #1, #2 and #6 still need the device-side fixes below.

### Per-Evolution-patch assessment for DerpFest 17 (Inference unless noted)
- **E1 (artifact path):** not needed on DerpFest 17. `DISABLE_ARTIFACT_PATH_REQUIREMENTS := true` is global in DerpFest's BoardConfigSoong.mk, and common_mobile.mk already allow-lists the gms /system apps (verified above). There is no AppDataBackup on DerpFest, and no GooglePackageInstaller in gms-17. Leave lineage_husky.mk without it.
- **E2 (maintainer):** use DerpFest's mechanism instead, i.e. the 16.2 "Add derpfest maintainer overlay" commit plus `DERPFEST_BUILD_TYPE` in lineage_husky.mk. Evolution's `build_maintainer_summary` string won't exist in DerpFest Settings.
- **E3 (system_other odex):** applies equally, since it comes from the AOSP BoardConfigMainlineCommon.mk inherited by zuma. It is optional; ART recompiles SystemUI on first boot. DerpFest's `DONT_DEXPREOPT_PREBUILTS := true` means GMS prebuilts aren't preopted at all, so the patch only matters for source-built apps (SystemUI, Settings, LineageParts/DerpFestParts).
- **E4 (zuma overlays vs ROM overlay names):** probably **no build error** on DerpFest 17. gms-17 suffixes every overlay `_GMS` (module and package), vendor/overlay has no such names, and Lineage zuma's names stay unique. If a collision appears, use DerpFest 16.2's rename-to-`…Zuma` commit, not Evolution's deletion: deleting would leave Pixel config values uninstalled, because DerpFest has no pixel-style superset. Runtime note: zuma's `PixelConfigOverlayCommon` and gms-17's `PixelConfigOverlayCommon_GMS` both apply to `android`; priority decides overlapping values.
- **E5 (default-permissions.xml):** **needed**, for a different reason than on Evolution. Both zuma and gms-17 use PRODUCT_COPY_FILES to the same destination. In AOSP's core/Makefile, duplicate PRODUCT_COPY_FILES destinations are de-duplicated (first wins, the rest go to product_copy_files_ignored) without a fatal error. So the build may pass while one file (Pixel device grants or GMS grants) is silently dropped. Apply the same rename (`default-permissions-zuma.xml`). The first-wins behaviour is from memory of build/make/core/Makefile and was not re-read in this session.
- **E6 (vendor duplicates):**
  - `DeviceIntelligenceNetworkPrebuiltAstrea`: **needed.** It is defined in both soong namespaces (TheMuppets `vendor/google/husky` and gms `common`) and both install to `product/priv-app/DeviceIntelligenceNetworkPrebuiltAstrea/`. Expect a Soong/Kati duplicate-install or "overriding commands for target" failure, as Evolution hit with its vendor/gms. Fix: drop the husky copy (Android.bp module + PRODUCT_PACKAGES).
  - `AICorePrebuilt-aicore_20260302.01_RC00`: same, but only if `WITH_GMS_AICORE := true`.
  - The 14 sysconfig XMLs: copy-file vs copy-file, so first-wins and **no build error expected** on DerpFest. Removing the husky lines is still cleaner and matches DerpFest 16.2's "Drop duplicated apps" approach.
  - `default-permissions_nowplaying.xml` and `preinstalled_packages_pixel_experience_2021_and_newer.xml`: **keep them** on DerpFest. gms-17 doesn't ship them; Evolution removed them only because its vendor/gms does.
  - Also check `CarrierSettings`, which DerpFest 16.2 dropped. gms-17's Android.bp was not seen to define it, so it was not flagged.
- **E7 (nowplaying_app_26q1.xml):** **not needed.** gms-17 has no nowplaying files, so keep the husky copy or Now Playing loses its sysconfig.
- **E8 (gpuflag):** **needed.** It is runtime-only (no build error). The blobs are identical TheMuppets lineage-24.0 and the zuma sepolicy comes from Lineage, which has no gpuflag domain per the Evolution finding. DerpFest's forked hardware/google/pixel-sepolicy is unlikely to add one (not verified). Apply the same three-line removal.
- **E9 (BODEGA):** Evolution-only (needs Evolution's ExtremeChargingController). Skip unless DerpFest frameworks have an equivalent.
- **DerpFest-specific risks with no Evolution counterpart:**
  - Face unlock: derpfest.mk installs ParanoidSense when `TARGET_FACE_UNLOCK_SUPPORTED` defaults to true. Lineage zuma (2026-10-16) now enables the Pixel face HAL path and copies `android.hardware.biometrics.face.xml` to vendor. Two face providers is a runtime conflict risk (the paths differ, so no copy-file clash). Consider `TARGET_FACE_UNLOCK_SUPPORTED := false` in device-husky.mk.
  - Google battery: `TARGET_DOES_NOT_SUPPORT_GOOGLE_BATTERY ?= true` installs TurboAdapter_NoBatt alongside gms TurboAdapter. husky has google_battery (`HUSKY_PERF_CHARGING_PLAN.md` F4), so set `TARGET_DOES_NOT_SUPPORT_GOOGLE_BATTERY := false`. Unverified whether TurboAdapter_NoBatt `overrides` TurboAdapter.
  - Quick Tap: ColumbusService is added unless `TARGET_SUPPORTS_QUICK_TAP := false`. Pixel 8 Pro supports Quick Tap; check for a duplicate with any blob Columbus package.
  - Place any `PRODUCT_*` "broken" variables in device-husky.mk, not BoardConfig, to avoid the read-only error RisingOS hit. Place `BUILD_BROKEN_*` in BoardConfig.
- **Firmware / kernel:** keep the Evolution README's firmware rule (OTA firmware ≥ phone's; CP3A.261005.005 bootloader ripcurrent-17.0-15681527 and radio g5300i-260604-260807-B-16036236 per README) and use Lineage `build_kernel`. DerpFest's manifest already carries Lineage's gs-6.1 kernel sources at branch 17 (verified). Running `m` before `build_kernel` leaves `device/google/shusky-kernels/6.1` without the prebuilts it needs if the shallow clone lacks them (the shallow clone is verified; that it lacks them is inference from the README's ordering).
